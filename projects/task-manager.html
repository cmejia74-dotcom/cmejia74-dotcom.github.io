DWG CM-002 · INDEPENDENT PROJECT · BUILT

Automated Task Management System

A desk device you hold and talk to. It captures speech on-board, ships the audio to a server that transcribes it and runs it through a language model, then draws the extracted task back on its own screen — all running off a single lithium cell.

SHEET A DESIGN INTENT CM-002

Capture a task in the two seconds before you forget it.

DESIGN CONSTRAINT

“Speak, and the task is on the screen — no phone, no app, no typing.”

Every task app I used had the same failure mode: the friction of unlocking a phone and finding the right screen was longer than my memory of the task. So I built a single-purpose object that does one thing — hold it, speak, and the task appears.

The hard part is that four systems have to talk to each other. An I2S microphone puts out a continuous 16 kHz audio stream. An ESP32 has to buffer that stream and push it over Wi-Fi without freezing the display it is also driving over SPI. A server has to catch the raw audio, transcribe it, and get a language model to figure out what the task actually is. Then the result has to land back on a 2.8" screen fast enough to feel instant.

Because the microcontroller is capturing audio and driving the display at the same time, the real work was timing and buffering — keeping the audio pipeline fed while the touch controller and screen stayed responsive.

SHEET B BUILD LOG 03 STAGES
01
STAGE 01 · DISPLAY BRING-UP

Prove the screen before anything else

Nothing else can be debugged until you can see something. The first milestone was getting the ILI9341 driven over SPI — wiring the four control lines, sorting out the chip-select and reset pins, and drawing a single filled rectangle.

A blue square is a deliberately boring target, and that is the point: it confirms the SPI bus, the pin mapping, the supply rail, and the display initialization sequence are all correct in one shot. Once the rectangle rendered, every later bug had a known-good foundation underneath it.

  • SPI VERIFIED
  • PIN MAP LOCKED
  • 3.3 V RAIL OK
02
STAGE 02 · INTERFACE & AUDIO

A real interface, and a microphone behind it

With pixels under control, the square became an actual UI: a header that reports the live task count, an empty state, and a full-width hold-to-speak control. Touch comes from an XPT2046 resistive controller sharing the SPI bus with the display, so the two had to be arbitrated rather than left to collide.

Behind the screen, the INMP441 streams 32-bit samples at 16 kHz over I2S. Holding the button opens a capture window and starts filling a buffer; releasing it closes the window and sends the buffer over the network. This is where latency either works or does not — the buffer has to drain to Wi-Fi at least as fast as the microphone fills it, or the audio breaks up.

  • TOUCH UI
  • I2S CAPTURE
  • 16 kHz · 32-BIT
  • SHARED SPI BUS
03
STAGE 03 · POWER & UNTETHERING

Off the bench supply, onto a cell

A device you pick up cannot be bolted to a laptop. Power moved to a Samsung 35E 18650 cell — 3500 mAh, flat-top — carried on an 18650 charge shield that regulates the 5 V and 3.3 V rails and provides pass-through charging.

The requirement that drove the part choice was no auto-shutoff. Most cheap power banks cut output when current draw drops below a threshold, which would kill an idle device sitting on a desk waiting to be spoken to. A shield with UPS-style pass-through keeps the ESP32 alive while charging and holds it up through the current spike when the Wi-Fi radio transmits.

  • 3500 mAh
  • 5 V / 3.3 V REGULATED
  • PASS-THROUGH CHARGE
  • NO AUTO-SHUTOFF
SHEET C SIGNAL PATH VOICE → TASK

One round trip, four hand-offs

The device itself stays simple. It captures and displays; the interpretation happens off-board. That split keeps the ESP32 doing what it is good at — real-time I/O — and puts the heavier work where there is enough memory to do it.

SHEET D BILL OF MATERIALS 06 SUBSYSTEMS

Hardware stack

Each part picked for a reason, grouped by the subsystem it belongs to.

01 · CORE
  • ESP32 development board The physical client. Holds the Wi-Fi link, routes power, and manages the inputs and outputs.
02 · INTERFACE
  • ILI9341 2.8" TFT LCD SPI-driven color display carrying the UI — task list, empty state, and the record control.
  • XPT2046 touch controller Resistive touch layer over the panel, sharing the SPI bus with the display.
03 · AUDIO
  • INMP441 digital microphone Omnidirectional I2S mic streaming 16 kHz, 32-bit samples. Digital output keeps the signal clean with no analog front end to design.
04 · POWER
  • 18650 charge shield V3 Regulates 5 V and 3.3 V with UPS-style pass-through charging and no auto-shutoff, so an idle device stays awake.
  • Samsung 35E 18650 cell 3500 mAh flat-top lithium-ion — enough headroom for the Wi-Fi transmit spikes.
05 · PROTOTYPING
  • Solderless breadboard Base for the build while the pin map was still moving.
  • Jumper wires Data and power runs between the boards — visible in every plate above.
06 · OFF-BOARD
  • Python / FastAPI server Local endpoint that catches the raw audio payload from the device.
  • Transcription + LLM APIs Speech-to-text, then a language model that reads the transcript and extracts the actual task.
SHEET E ENCLOSURE FUSION 360

Turning a breadboard into an object

The electronics work, but a loose breadboard is not a product. The enclosure is modeled in Fusion 360 as a two-part clamshell: the display and touch panel mount to the lid, and every microcontroller, jumper and battery lives underneath, out of sight.

The lid is on a hinge rather than screws, so the internals stay reachable — the wiring is still changing, and a case you have to destroy to open is a case you stop opening. The cutouts are sized to the bare board rather than the module, the cable path clears the hinge swing, and there is room to swap the 18650 without tearing the wiring apart.
